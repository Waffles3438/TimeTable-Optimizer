# Per-course lecture instructor preference search and UI integration

This change adds strict `firstName` + `lastName` instructor identities, carries lecture provenance alongside generated meeting choices, and exposes per-course instructor checkboxes in the page. Selected identities flow through `buildCoursePlans`, are evaluated once per course, and are ordered after the existing lunch and schedule objectives. The focused identity, provenance, objective, and UI tests pass, but real-catalog exact-search validation exposes a severe scalability regression when a preference is active, and the no-preference candidate domain is also much larger than before. Watch for: **confirmed** global preference-aware search disables the search bounds and memoization; **confirmed** provenance-aware deduplication leaks into no-preference searches; **confirmed** the new preference/provenance payload is not covered by a worker structured-clone test.

**Verdict**: NEEDS_CHANGES

## High-level view

**confirmed** — Any nonempty course preference switches the entire exact search into a mode with no subset caches, objective-state memoization, lunch-completion memoization, or schedule bounds. A representative three-course slice that completes without a preference does not finish within 120 seconds after selecting one valid lecture instructor.

**confirmed** — The no-preference branch now keys candidates with full option signatures, which include section names and lecture instructor provenance, rather than only typed meeting schedules. On the current six-course `computer-1-fall` cache this retains 228,705 candidate descriptors where the previous event-equivalence key retains 61,635.

**confirmed** — The worker source remains a thin delegate, but the worker test uses only a tutorial fixture and records the result object directly instead of exercising a structured-clone round trip for `preferredInstructors` and `lectureProvenance`.

### Global preference-aware exact search

**confirmed** — `web/optimizer.js:1455-1458` enables `preferenceAwareSearch` if any course has a nonempty preference list. That one global flag disables subset caches and subset tables at `1766-1787`, removes objective-state memoization at `2747-2763`, bypasses active-day and objective pruning at `2391-2416`, and removes lunch-completion memoization at `2898-2932`. The traversal remains exhaustive, but it has no schedule lower bound or repeated-state reuse once one course has an active preference. On the current `computer-1-fall` APS100H1/APS110H1/APS111H1 slice, the no-preference search completed in about 1.1 seconds after visiting 102,502 states; selecting the valid `dawn kilkenny rocheleau` preference for APS100H1 did not complete within 120 seconds. Preference-aware bounds and memo keys need to retain the provenance-relevant state, or schedule pruning must remain active for unaffected state, before this can be considered usable on the catalog.

### Provenance-aware candidate deduplication

**confirmed** — `web/optimizer.js:1603-1611` constructs `eventEquivalenceKey` from `optionSignature`, whose lecture form includes section names and instructor provenance (`400-445`), and then uses that key even when `preferenceAwareSearch` is false. Two candidates with identical typed meetings therefore remain separate when only section/instructor metadata differs, although no preference objective can distinguish them. Counting the current six-course cache by these keys gives 228,705 retained candidates; applying the event-only key from `main` gives 61,635. The no-preference branch should restore event-equivalence deduplication, while only courses with active preferences retain provenance-distinct candidates.

### Worker/page preference round trip

**confirmed** — The worker integration test at `tests/test_frontend_optimizer.js:3915-4006` executes `web/optimizer-worker.js`, but its fixture has only a TUT section and `postMessage` stores the result object directly. The test does not send a lecture option with `preferredInstructors` and aligned `lectureProvenance`, nor clone the terminal message as a browser `postMessage` would. Add a worker-context test using an identical-time preferred/nonpreferred lecture pair and a structured-clone round trip so field loss or serialization changes cannot silently bypass the page’s result guards.
